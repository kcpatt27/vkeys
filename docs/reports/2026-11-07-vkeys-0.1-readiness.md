## What is proven

### Raven broker deployment (003)

The broker is installed on Raven and runs as a dedicated `vkeys` system user:

- `/etc/vkeys` holds the master key and profiles; `/var/lib/vkeys` holds the
  vault and audit log; binaries are in `/usr/local/bin`.
- `vkeys-broker.service` is active and enabled, bound to `127.0.0.1:8787`.
- `/healthz` returned HTTP 200 with
  `{"budget_usd":5.0,"ok":true,...}` after a real completion.
- The OS-user boundary holds: the agent user cannot read `/etc/vkeys/master.key`, and
  `~/.config/vkeys/broker.token` is mode `0600`.

This is the strong boundary described in `README.md` and `SECURITY.md`: the
provider key stays in the broker process, and the agent gets a use-only token.

### Windows SYSTEM broker running (2026-11-09)

The Windows installer ran elevated on a live host:

- install exited 0; the `vkeys-broker` scheduled task is Running;
- `/healthz` returned HTTP 200 with
  `{"budget_usd":5.0,"ok":true,"spent_usd":8E-06}`;
- the agent user cannot open `vault.bin` or `master.key`; it can read only
  `%APPDATA%\vkeys\broker.token`;
- a 1-token completion through the broker returned HTTP 200.

The run fixed installer defects: non-inheritable directory ACLs, an ACL that
left logon-session read access on the master key, silent `vkeys set` failures,
no broker stop before replacing binaries, and a budget without prices.

Boot start is verified: after a reboot at 07:30:12, the task chain started at
07:30:26 and the broker at 07:30:33; `/healthz` returned 200. 004 is closed.

### Raven installer binary check (already fixed)

`deploy/raven/install.sh` now tests `-f` for both binaries and runs
`chmod +x` before installing them (`install.sh:36-37`). This matters for the
Raven bundle: files copied from Windows through `scp` can arrive without the
execute bit, so the old `-x` precheck failed before the installer had a chance to
fix the mode.

### Raven profile budget bug (already fixed live)

The first Raven profile set a `$5` budget without `--price-in`/`--price-out`.
`config_with` rejects a positive budget when both prices are zero
(`rust/src/broker.rs:282-283`), so the broker refused to start. The live profile
now passes:

```text
--budget-usd 5.00 --price-in 0.30 --price-out 1.20 --audit /var/lib/vkeys/audit.jsonl
```

`deploy/raven/profiles.toml:5` carries exactly those values. The `/healthz`
response above shows the live budget as `5.0`, which matches.

### Raven package integrity

- Bundle: `dist/raven-arm64` and `dist/vkeys-0.1.0-raven-arm64.tar.gz`
  (3,996,822 bytes). The tarball contains both binaries, the four `deploy/raven`
  files, `README-RAVEN.md`, and `SHA256SUMS`.
- This check re-ran `Get-FileHash` against every entry in
  `dist/raven-arm64/SHA256SUMS`: all 7 entries match.
- The repo copies of `install.sh`, `profiles.toml`, and
  `vkeys-broker.service` are byte-identical to the bundle copies.
- The repo copy of `deploy/raven/README.md` now differs from the bundle copy in
  two ways: this report corrected its Windows note after the bundle was built
  (the bundle copy still says the Windows equivalent is not built), and the
  verifier normalised the em dash in its title. Documentation-only deltas;
  rebuild the bundle before shipping if they matter.
- The bundle README records the build as `main` at `e73b16f` on 2026-11-06,
  `aarch64-unknown-linux-gnu`, Rust 1.99.1. The commit matches HEAD, but the
  bundle is not a pure `e73b16f` tree: its `install.sh` carries the uncommitted
  `chmod +x` fix, so it does not match `HEAD:deploy/raven/install.sh`. The
  bundle is only reproducible from a tree with that fix committed.

```bash
curl -fsS http://127.0.0.1:8787/healthz; echo
sudo systemctl is-active vkeys-broker
sudo systemctl is-enabled vkeys-broker
sudo -u <agent-user> test -r /etc/vkeys/master.key && echo "BAD: agent can read key" || echo "ok: key unreadable"

```

### Tag

```powershell
git tag -a v0.1.0 -m "vkeys 0.1.0"
git push origin main
git push github main
git push github v0.1.0
```

### Publish to crates.io

Human-only. The profile injects `CARGO_REGISTRY_TOKEN` for `cargo publish`:

```powershell
cd rust
vkeys run publish-vkeys
```

### Build and attach artifacts

`release-artifacts.yml` runs manually or when a GitHub release is published. It
builds but does not publish. Download the artifacts, verify them, and attach
them to the release. The x64 archives must be rebuilt at the release commit and
checked, not assumed: the last green run predates the three broker commits now
on `main`.

### Flip the host

Only after the crate is live:

```powershell
gh repo edit kcpatt27/vkeys --visibility public --accept-visibility-change-consequences
```

Then create the GitHub release from `v0.1.0`.

### Re-enable CI after the flip

Add `push` and `pull_request` to `.github/workflows/ci.yml`, push through a
branch and merge, then run the workflow once. Confirm the matrix is green and
that `release-artifacts.yml` fires on a published release.

### Rollback

A published crate version cannot be deleted, only yanked:

```powershell

cargo yank --version 0.1.0 vkeys
```
